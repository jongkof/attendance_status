# 관리자 접근

## Decisions

- 관리자 기능(`/admin` 아래 모든 화면과 그 화면이 부르는 서버 요청)은 관리자 공용 비밀번호 하나로 잠근다. 로그인에 성공하면 만료가 있는 서명된 쿠키로 세션을 유지한다.
- 처음 비밀번호는 서버 환경 변수로 정한다. 관리자가 화면에서 비밀번호를 바꾸면 암호화한 값(해시)만 데이터베이스에 저장하고, 그 뒤로는 저장된 값이 환경 변수보다 우선한다. 비밀번호 원문은 어디에도 저장하지 않는다.
- 비밀번호를 바꾸면 이미 로그인한 세션은 모두 풀린다.
- 비밀번호를 잊었을 때는 데이터베이스에 저장된 비밀번호 한 줄을 지워 환경 변수의 처음 비밀번호로 되돌린다. 이메일 복구는 두지 않는다.
- 잠금 검사는 화면 접근 때만이 아니라 데이터를 읽거나 바꾸는 서버 요청마다 그 안에서 다시 한다. 주소를 직접 호출해도 로그인 없이는 거절된다.
- 공개 현황표는 로그인 없이 누구나 볼 수 있다.

## Boundaries

- 이 결정은 "누가 관리자 기능을 쓸 수 있는가"만 정한다. 누가 무엇을 바꿨는지 구분하거나 기록하지 않는다.
- 새 관리 기능(개별 수정, 휴일·행사 편집, 명단 관리, 발송)도 같은 잠금을 쓴다. 관리 기능을 공개 주소에 따로 두지 않는다.
- 관리자 이메일 저장과 이메일 복구는 이 결정에 들어 있지 않다. 현황 메일 발송 작업에서 메일 서비스와 함께 정한다.

## Why

관리자는 한 명이거나 몇 명이 같이 쓰는 정도이고, 변경 기록의 요구가 없다. 계정 방식(Supabase 로그인)은 관리자 이메일을 외부 서비스에 저장해야 하고 가입·확인 메일 설정이 필요하다. 개인정보를 걱정하는 상황에서 저장하는 정보를 늘리지 않는 쪽을 택했다. 화면에서 비밀번호를 바꾸게 하려면 서버가 새 값을 저장할 곳이 필요해서 해시만 데이터베이스에 둔다. 이메일 복구는 메일을 보내는 외부 서비스와 관리자 이메일 저장이 함께 필요한데, 둘 다 발송 작업에서 정할 일이라 그때까지 미뤘다. Next.js 16 공식 문서도 `proxy`의 검사는 미리 돌려보내는 용도로만 쓰고, 실제 권한 검사는 데이터에 접근하는 서버 코드에서 하라고 안내한다.

## Reconsider when

- 관리자가 늘어 누가 바꿨는지 구분하거나 사람별로 접근을 끊어야 할 때
- 비밀번호를 잊는 일이 잦아 대시보드에서 지우는 복구가 부담이 될 때, 또는 현황 메일 발송용 메일 서비스가 정해졌을 때(이메일 복구를 다시 본다)
- 사내 인증(SSO)을 쓸 수 있게 될 때

## Still-rejected alternatives

- 관리자별 계정(Supabase 로그인) — 이메일을 외부 서비스에 두어야 하고 준비할 것이 많다. 위 재검토 조건이 생기면 다시 본다.
- `proxy`에서만 잠그는 방식 — 서버 요청을 직접 호출하면 우회될 수 있어 공식 문서가 권하지 않는다.
- 비밀번호를 환경 변수에만 두는 방식 — 안전하지만 화면에서 바꿀 수 없어 요구를 채우지 못한다. 화면에서 바꾸는 요구가 사라지면 다시 본다.
